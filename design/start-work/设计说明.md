# 开始工作流程方案

2026-10-23。本目录是独立交互原型，使用示例数据，不连接正式素材库、下载服务、AI 接口或发布账号。

## 设计结论

用「五阶段路线 + 当前待办 + 自动制作计划」组织开始工作：

**准备素材 → 确认方案 → 自动制作 → 检查成品 → 导出发布。**

阶段始终固定。字幕、文案、封面等可选功能放进阶段内部，不把所有工具都变成必经步骤。入口以使用已有剧集制作成片为主；AI 视频生成保留为单独任务类型。

用户每次回到页面，应能在首屏回答：现在做哪部剧、做到哪里、还缺什么、下一步点哪里。软件运行期间明确显示「软件正在做」，需要用户决定时显示「需要你确认」。

## 当前项目的具体问题

本轮直接核对 `web/index.html`、`web/app.js`、`web/workflow.js`、`web/source_workspace.js`、`web/progress.js` 和 2026-10-23 的连续制作衔接说明。现有版本已经具备连续制作、任务配置快照、单步合并后接续等基础；本方案利用这些能力。

1. 导航按功能罗列：预处理、去重设置、编码、字幕、文案、成本、发布等同级出现，顺序不能代表实际必做顺序。
2. 页面内的「开始连续制作」「仅合并切分」与固定底栏「开始制作」并存，且页面按钮使用当前剧集、底栏使用勾选剧集，目标范围需要用户自行理解。
3. 右侧有执行计划，但开始前没有统一的准备清单解释缺少接口、未选择集数、样片未确认等条件。
4. 软件制作步骤与人工动作混在同一理解层次。比如字幕修复是机器工作，确认修复效果是人的工作。
5. 制作结束、人工验片、材料导出、平台提交的完成条件不同，需要分别显示。

旧截图只用于理解现有布局，不作为本轮正式客户端的实时运行验收。

## 每个阶段的操作合同

| 阶段 | 用户要做什么 | 软件做什么 | 完成条件与下一按钮 |
| --- | --- | --- | --- |
| 1 准备素材 | 选择本地导入或在线采集；选剧、选集、确认顺序 | 扫描或下载并校验，显示实际已入库数量 | 本次选择的所有源文件已就绪且选择非空；「下一步：确认方案」 |
| 2 确认方案 | 选择制作方案、分集方式、输出尺寸；按需选择字幕修复、文案、包装、封面、工程和成本 | 列出本次启用步骤，按需检查模型接口、引擎、选区、费用信息 | 无阻断项；涉及字幕或明显画面变化时完成有效样片确认；「开始自动制作」 |
| 3 自动制作 | 查看当前处理内容；需要时暂停或修复问题 | 使用提交时的参数快照执行已启用步骤，更新真实进度 | 本次必需步骤全部成功；「下一步：检查成品」；失败时「从失败步骤继续」 |
| 4 检查成品 | 抽查头、中、尾片段及音画、字幕、封面和文案 | 展示真实产物、来源任务、预览与缺失项 | 人工确认本次产物；有问题返回对应设置并明确影响范围；「确认通过，准备导出」 |
| 5 导出发布 | 核对文件和材料，选择导出；自行前往平台提交 | 生成材料包和清单；显示真实导出结果 | 本地导出完成；平台状态保持「待提交」，依据真实结果另行更新 |

在线下载与导入必须区分「下载成功」和「已入库可制作」。缺集时分别提供「重试缺失集」或「只使用已入库集并重新确认」，不默默跳过。这里的原型只演示结果状态，不执行下载。

## 界面与交互方案

- 顶部固定展示五阶段，已完成、当前、未开始都有文字；未来阶段不能绕过前置检查。
- 主区标题直接说明当前要做的动作。阻断项贴近相关选项，解释如何修复。
- 右侧显示当前剧集、所选集数与顺序、本次执行计划、下一次人工动作。准备阶段标为「计划」，运行后标为「本次任务」，使用任务快照。
- 每阶段只设置一个醒目的主按钮，文字描述结果。辅助操作为次按钮，避免多个「开始」竞争。
- 首次进入从素材开始；以后从该剧集和任务的真实状态恢复，展示上次做到哪里。用户可返回修改准备项。
- 有经验用户可以复用上次方案；仍需检查本次来源、接口和样片有效性。
- 当前预处理、字幕、文案、编码等页面保留为工具，在阶段内通过「调整」入口打开，保存后回到原阶段和滚动位置。
- 单步操作放进「单独处理」工具；已完成的合并任务显示「复用已完成分集继续制作」，沿用现有接续校验，不暗示已经执行字幕处理。
- 任务状态枚举与当前后端一致：排队、处理中、正在暂停、已暂停、待恢复、失败、已停止、已完成；「需要你确认」是工作流层状态，不能伪装成后台任务在运行。

## 制作计划与依赖

连续制作沿用当前真实顺序：可选 AI 剧名简介 → 可选源片字幕修复 → 画面与分集 → 可选成片包装 → 可选封面 → 可选工程记录 → 可选成本报告。

- 字幕修复在合并前覆盖本次所选源片；开始前检查引擎/服务、选区、样片确认。
- AI 文案只在启用时检查对应文字连接；未启用时使用原剧名和简介。
- 自动封面默认本地排版；选择 AI 底图时才检查生图连接。连接存在与接口调用成功是不同证据。
- 成本报告只在启用时检查实际成本数据，不自动填造金额。
- GPU 不可用按已有实现回退 CPU；界面解释实际路径，不因「勾选 GPU」就标为已使用。
- 每集时长与源片总时长只能给粗略分集数量。变速、包装份数与尾段会改变实际输出；无法可靠计算耗时时显示「开始后估算」，不编造剩余时间。

## 失效与恢复规则

样片确认应绑定源文件版本、集数顺序、字幕模式/选区、画面设置和引擎/模型等会改变效果的参数。任何相关变化都让确认失效；单纯更改成本金额不需要重新试片。原型演示素材/集数与字幕方案变化后的失效，正式接入应做完整指纹。

已提交任务的配置快照保持不变。修改全局设置不改变旧任务计划。重新制作需创建新任务，并显示复用与重做范围；选集或源文件变化时按现有后端检查停止不合法接续。

失败时同时显示「失败步骤」「已保留哪些产物」「怎么修复」「从哪里继续」。仅当后端检查点有效时提供恢复。任务完成后不自动替用户勾选人工验片，不自动标记平台审核通过。

## 视觉计划与自检

- 沿用工作台的浅色底和紫色强调：工作底色 `#F7F8FC`、内容纸面 `#FFFFFF`、主文案 `#272438`、辅助文案 `#696577`、操作紫 `#6549C7`、确认绿 `#217150`。颜色还必须配合文字与图标表达状态。
- 中文以本机 Microsoft YaHei / Segoe UI 为主，避免为流程原型增加网络字体依赖；正文 15px，当前动作标题 24px，辅助说明不低于 12px。
- 左侧保留工作台语境；五阶段路线居上；主区展开当前动作；右侧以制作清单的形式显示计划。窄窗口改为上下排列。
- 本方案的视觉重点是有实际顺序的五阶段路线，避免无意义统计、营销横幅和无差别卡片。
- 本地技能库两次流程检索未匹配到适用条目，设计系统检索的营销型结构也不适合桌面生产工具，未采用；只采用通用的可访问性、明确反馈、清晰层级等指导。流程依据以下官网原始资料和现有项目。

## 网络依据与项目化推断

1. [GOV.UK：Complete multiple tasks](https://design-system.service.gov.uk/patterns/complete-multiple-tasks/)：长事务适合任务清单；相关动作应分组，明确完成状态，重新进入时给出总览。对应本软件的制作待办与返回继续。
2. [IBM Carbon：Progress indicator](https://www.carbondesignsystem.com/building-blocks/core/components/progress-indicator/guidelines)：线性多阶段显示已完成、当前和未来阶段。任意顺序或阶段数不断变化的流程不适合硬套，所以本方案保持五个主阶段固定，把可选项留在内部。
3. [NN/g：Wizards](https://www.nngroup.com/articles/wizards/)：向导可降低不熟悉流程时的负担，频繁使用者也需要更快的路径。因此采用可返回的工作台和复用方案，不做强制重复走完的弹窗。

「五阶段」「人机分工」「制作前预检」「按任务恢复」是根据本项目提出的设计建议，不是官网替本产品做出的结论。

## 正式接入的最小改造

1. 新增开始工作页和按剧集保存的工作流状态。按用户追加要求，保留「引导流程 / 原版工作台」两个入口，并记住选择；原版的功能导航和操作方式继续可用。
2. 增加统一、只读的准备情况计算：源文件与选集、启用步骤、接口/引擎依赖、样片指纹、输出路径；后端入队前继续做权威校验。
3. 让页面内按钮和全局底栏共享同一份目标选择与配置草稿；提交前明确剧集、集数、范围和已启用步骤。
4. 复用现有 `pipeline`、`workflowPlan`、制作进度、暂停恢复、`continueFromJob` 和产物记录，减少对处理引擎的改动。
5. 补充「制作已完成 / 验片已确认 / 材料已导出 / 平台待提交」的独立状态，禁止自动相互推导。

验收重点：首次进入知道第一步；缺一项能直接修复；开始一次自动串行；暂停/失败/重开能定位；修改参数不会篡改旧任务；成品待验收和平台待提交不会被误报完成。

## 原型范围

`index.html` 可直接打开，也可通过本地静态服务预览。可演示：素材为空、选集、制作方案、字幕样片确认、缺少接口、自动运行、暂停、故障恢复、人工验片、导出和平台待提交。页面中的素材、进度、环境和文件均为示例；演示操作不调用正式后端。正式程序源码和安装包未在本方案中修改。
